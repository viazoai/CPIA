# CPIA PoC 실행계획

> **개인과제 | 2026년 5~6월 | 조형준 프로**
> 기획서 `design/CPIA_기획서_v6.md` 기반 실증 계획

---

## 이 문서의 목적

한 달 안에 "**Collector → Parser → Validator → Reporter → Forecaster → Dashboard, 전체 파이프라인이 실제로 돌아간다**"는 것을 경영진 앞에서 라이브로 보여주는 것.

> **핵심 전략:** 공종 범위를 좁히되 전체 스토리를 완성한다.
> "모든 공종을 처리하지만 보고서 생성까지만" 보다
> "2~3개 공종이지만 D-14 리스크 탐지 + 대시보드까지 전부" 가 경영진에게 훨씬 강하게 전달됩니다.

## 1. PoC 범위 결정

### 포함 범위

| 구분 | 내용 |
|------|------|
| **대상 현장** | Y-1 Ph-1 OBL 단일 현장 |
| **대상 공종** | **2~3개 공종 선택 집중** (철근·거푸집·콘크리트 등 물량 데이터가 명확한 공종) |
| **구현 Agent** | **5개 전체:** Collector → Parser → Validator → Reporter → Forecaster |
| **입력 데이터** | 샘플 작업일보 5~10개 + 가상 과거 실적 데이터 (2~3개월치) |
| **출력물** | 자동 생성 Daily Report + **경영진 대시보드 (Streamlit)** |
| **Human-in-the-Loop** | 이상치 감지 시 웹 UI 또는 터미널 승인 |

### 제외 범위

| 제외 항목 | 이유 |
|----------|------|
| 6개 현장 확산 | 1개 현장 완성 후 확산은 반복 작업 — PoC 이후 |
| 이메일·카카오톡 실제 연동 | 보안 승인 절차 시간 소요 — 파일 드롭 방식으로 대체 |
| Forecaster 예측 정확도 검증 | 실데이터 2개월치 없음 — 가상 히스토리로 흐름 증명, 정확도는 Phase 2 과제 |
| 전체 공종 처리 | 2~3개 공종만으로도 파이프라인 전체를 보여줄 수 있음 |

### 핵심 증명 명제

> "선택한 공종의 작업일보를 넣으면, AI가 이상치를 감지하고 보고서를 만들며,
> 추세를 분석해 D-14 리스크를 탐지한다. 경영진은 대시보드 한 화면으로 현장 상황을 본다."

## 2. 제작 방식

### 기본 방침

**"단순하게, 동작하게, 경영진이 이해하게"**

- 로컬 Python 환경에서 실행 가능한 수준으로 구현 (복잡한 인프라 불필요)
- Forecaster는 가상 히스토리 데이터로 흐름을 증명 — 예측 정확도는 PoC 목표가 아님
- 대시보드는 코드보다 **화면이 설득**한다는 원칙으로 설계

### 기술 선택

| 결정 사항 | 선택 | 이유 |
|----------|------|------|
| Agent 프레임워크 | LangGraph | H-i-L interrupt·조건 분기·병렬 실행이 핵심 |
| LLM 모델 | Claude Sonnet 4.6 (Parser·Reporter) / Opus 4.7 (Forecaster) | 기획서 설계와 동일 |
| 입력 방식 | 지정 폴더에 파일 드롭 | 이메일 연동 대신 — 개념 증명에 충분 |
| 대시보드 | **Streamlit** | Python만으로 빠르게 웹 UI 구성 가능, 데모용으로 최적 |
| Forecaster 데이터 | 가상 히스토리 (2~3개월치 합성 데이터) | 실데이터 없는 PoC 환경에서 D-14 흐름 증명 |
| 실행 환경 | 개인 PC (로컬) | 사내 인프라 승인 전 단계에서 빠르게 검증 |

### 데모 시나리오 (경영진 시연 기준)

```
[화면 1: 대시보드 초기 상태]
```

## 3. 사전 준비 사항

### A. 데이터 준비 (가장 중요한 선행과제)

| 필요 데이터 | 형태 | 확보 방법 | 비고 |
|------------|------|----------|------|
| 작업일보 샘플 5~10개 | Excel 또는 텍스트 | Y-1 현장 담당자 요청 (비식별화) | 못 받으면 가상 데이터로 대체 가능 |
| WBS 구조표 (공종 목록) | Excel | 현장 PM에게 공종·Activity 목록 요청 | **2~3개 공종만 선택하면 충분** |
| Plan 공정률 곡선 | Excel | 공정 담당자에게 계획 진도율 요청 | S-curve 원본 불필요, 기준값만 있으면 됨 |
| **과거 실적 데이터** (2~3개월치) | Excel 또는 직접 생성 | 현장 요청 또는 **가상 데이터 합성** | Forecaster 학습용 — PoC에서는 가상으로 충분 |

> **현실적 대안:** 현장 데이터를 못 받더라도 양식 구조만 파악하면 가상 데이터로 전체 파이프라인 구현 가능.
> 단, 시연 시 "샘플 데이터 기반입니다"를 명시하면 됩니다.

### B. API 및 개발환경

| 항목 | 확인 사항 | 예상 비용 |
|------|----------|---------|
| Claude API Key | Anthropic 계정 발급 | PoC 기간 $10~20 예상 (Opus 포함) |
| Python 환경 | 3.11+ / LangGraph·anthropic·streamlit 설치 | 무료 |
| 사내 AI 인프라 | PoC는 로컬 PC로 가능, 본격 운영 시 필요 | 향후 IT 협의 |

### C. 현장 협조 요청

| 대상 | 요청 내용 | 소요 시간 |
|------|----------|---------|
| Y-1 현장 담당자 1명 | 작업일보 양식 확인, 보고서 샘플 검토 | 미팅 1~2회 (각 30분) |
| 공정 담당자 (선택) | 공종 선택 + 공정률 산출 기준 확인 | 미팅 1회 (30분) |

> 현장 협조는 데이터 제공보다 **"이 보고서가 실제로 쓸 만한가"** 피드백이 목적입니다.
> 1시간 투자로 데모 완성도가 크게 달라집니다.

## 4. 단계별 진행 계획 (4주)

### Week 1 — 기반 구축

**목표:** 개발 시작 가능한 상태 + 데이터 확보

- [ ] 개발 환경 구성 (Python, LangGraph, anthropic, streamlit 설치·테스트)
- [ ] 현장 담당자에게 작업일보 샘플 요청
- [ ] 대상 공종 2~3개 선정 (철근·콘크리트·거푸집 등 물량 명확한 공종)
- [ ] 샘플 작업일보 확보 또는 동일 양식 가상 데이터 5개 생성
- [ ] Forecaster용 가상 히스토리 데이터 생성 (선택 공종 2개월치 합성)
- [ ] LangGraph 파이프라인 뼈대 (노드·엣지 구조만) 구성

**Week 1 체크포인트:** 데이터 5개 + 히스토리 데이터 있고, 파이프라인이 빈 껍데기로 실행된다.

---

### Week 2 — 수집·파싱 파이프라인 (Collector + Parser)

**목표:** "파일을 넣으면 구조화 JSON이 나온다"

- [ ] Collector: 지정 폴더 파일 감지 + Excel·텍스트 텍스트 추출
- [ ] Parser: Claude Sonnet 4.6으로 비정형 텍스트 → WBS 매핑 JSON 변환
  - 프롬프트에 선택 공종 WBS 구조 명시 (정확도 향상 핵심)
  - 인원·물량·진도율 필드 추출
- [ ] Parser 정확도 확인: 샘플 5개 중 4개 이상 정상 매핑 목표
- [ ] 현장 담당자에게 Parser 출력 결과 1차 검토 요청 (30분 미팅)

**Week 2 체크포인트:** 샘플 5개 → 구조화 JSON 5개 생성된다.

---

### Week 3 — 전체 파이프라인 완성 (Validator + Reporter + Forecaster + H-i-L)

**목표:** "이상치 감지 → 담당자 승인 → 보고서 생성 → D-14 탐지까지 한 번에 돌아간다"

- [ ] Validator: 이상치 감지 룰 구현 (전일 대비 ±30% / σ 2.0 초과)
- [ ] Human-in-the-Loop: LangGraph interrupt로 이상치 발생 시 승인 대기 구현
- [ ] Reporter: 승인 후 Daily Report 자동 생성 (공정률 요약·BP별 현황·이상치 메모)
- [ ] Forecaster: Claude Opus 4.7로 가상 히스토리 + 현재 실적 → 추세 분석·D-14 탐지
  - 만회 시나리오 3안 자동 생성 포함
- [ ] Reporter·Forecaster 병렬 실행 구성 (LangGraph Send() API)
- [ ] End-to-End 통합 테스트: 파일 드롭 → 대시보드 업데이트까지 전체 흐름 확인

**Week 3 체크포인트:** 이상치 삽입된 샘플로 전체 5개 Agent가 순서대로 실행되고 D-14 알림이 출력된다.

---

### Week 4 — 대시보드 + 경영진 데모 완성

**목표:** "경영진이 보는 화면"과 "5분 시연 시나리오"

- [ ] Streamlit 대시보드 구현
  - 공정률 현황 (계획 vs 실적 S-curve)
  - 이상치 알림 현황 (발생·처리 이력)
  - D-14 리스크 지표 (색상 코드: 정상·주의·위험)
  - 최신 Daily Report 링크
- [ ] 파이프라인 실행 결과 → 대시보드 자동 반영 연결
- [ ] 데모 시나리오 리허설 (5분 기준)
  - "지금 누르면 뭐가 되는지" 를 경영진이 따라올 수 있게 구성
  - AS-IS(수작업 3시간) vs TO-BE(AI 5분) 비교 슬라이드 1장 포함
- [ ] 결과 문서화: 무엇이 됐고, 실운영으로 가려면 무엇이 필요한지

**Week 4 체크포인트:** 라이브 데모 가능. 경영진 앞에서 실제로 실행 가능한 상태.

## 5. PoC 성공 기준

경영진 시연에서 **아래 4가지를 실제로 보여줄 수 있으면** 성공입니다.

| # | 성공 기준 | 검증 방법 |
|---|----------|---------|
| 1 | 작업일보 파일 투입 → Daily Report 자동 생성 | 라이브 실행 |
| 2 | 이상치 감지 → H-i-L 승인 → 파이프라인 재개 | 이상치 케이스 삽입 데모 |
| 3 | D-14 리스크 탐지 + 만회 시나리오 3안 출력 | Forecaster 출력 화면 |
| 4 | 경영진 대시보드에서 현황·이상치·리스크 한 화면 확인 | Streamlit 화면 시연 |

**처리 시간 목표:** 전체 파이프라인 5분 이내 (vs. 수작업 2~3시간)

> **PoC에서 검증하지 않아도 되는 것:**
> Forecaster 예측 정확도, 시스템 운영 안정성, 보안 적합성 — 이는 Phase 2 과제입니다.
> "이런 흐름으로 작동한다"는 것만 보여주면 됩니다.

## 6. 리스크 및 대응

| 리스크 | 발생 가능성 | 대응 방안 |
|--------|-----------|---------|
| 현장 데이터 수령 지연 | 높음 | Week 1부터 요청 시작, 안 오면 가상 데이터로 선행 개발 |
| 작업일보 양식이 너무 다양 | 중간 | 2~3개 공종·양식만 선택해서 집중, 나머지는 Phase 2에서 |
| Parser 정확도 부족 | 중간 | 프롬프트에 WBS 구조 명시적 포함, 선택 공종 좁혀서 집중 |
| Forecaster 가상 데이터 신뢰도 | 중간 | 시연 시 "샘플 기반 PoC" 명시, 흐름 증명이 목적임을 설명 |
| 대시보드 개발 시간 부족 | 중간 | Week 4의 다른 항목 줄이고 대시보드 우선 — 경영진 시연의 핵심 |
| 4주 내 전체 완성 불가 | 중간 | Week 3 체크포인트(전 Agent 동작)까지만 해도 기술 증명으로 제출 가능 |

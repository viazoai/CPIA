## 2. 품셈 데이터 구조 — Forecaster 활용 가능성

### 2-1. 핵심 발견: 생산성 데이터가 있다

품셈_건설_v2.json에는 **"규격별 시공량(인원당 일일 생산량)"** 이 코드별로 포함되어 있다.

```
C-6-1-1  콘크리트 타설:
  인력운반_무근: 23 m³/일
  인력운반_철근: 20 m³/일
  장비사용_무근: 63 m³/일
  장비사용_철근: 55 m³/일

C-6-2-2  철근 현장가공:
  일반(TypeI):     4.5 ton/일
  복잡(TypeII):    4.0 ton/일
  매우복잡(TypeIII): 3.5 ton/일

C-6-2-3  철근 현장조립:
  Ⅰ-1(단순):      3.4 ton/일
  Ⅰ-2:            2.2 ton/일
  Ⅱ-1:            2.6 ton/일
  Ⅱ-2(복잡):      1.1 ton/일  ← 단순 대비 3.1배 차이

C-6-3-1  합판거푸집 설치·해체:
  제물치장: 20 m²/일
  복잡:     25 m²/일
  보통:     45 m²/일
  간단:     50 m²/일  ← 복잡 대비 2.5배 차이
```

### 2-2. 중요 이슈: 단일 기준값이 아니다

실행계획서는 `std_productivity: 2.30 (단일 값)`을 가정하고 있지만, **실제 품셈은 시공 복잡도·방법별로 다른 값을 가진다.**

| 문제 | 내용 | 영향 |
|------|------|------|
| 규격 다중값 | 콘크리트 타설 조건이 4가지(인력/장비 × 무근/철근) | Forecaster가 어떤 값을 기준으로 할지 결정 필요 |
| 조 단위 vs 인원 단위 | 품셈의 "일일 시공량"은 **팀(조) 기준**이고, 작업일보의 "금일실적"은 협력사 전체 투입량 | 단순 비교 불가 — 인원 구성 정보 필요 |
| 건설 vs 건축 부문 차이 | RC 공사 생산성은 C-6-x(공통) 에 있고, A-6-x(건축)는 방수공사 코드 | 코드 체계 혼용 주의 |

**결론:** 품셈 생산성 데이터 자체는 존재하고 활용 가능하지만, Forecaster 계산을 위해 **각 공종별 "PoC 기준값" 을 사람이 한번 결정**해서 매핑 테이블을 만들어야 한다. LLM이 자동으로 품셈에서 올바른 기준값을 뽑아오기는 어렵다.

## 3. WBS 공정표 구조 분석

### 3-1. 계층 구조

```
L1: Work Area (건물 구분 — FAB, CUB, UT 등)
  L2: Phase (공정 단계 — E/P/C/Pre-Com/Com)
    L3: Floor (층)
      L4: Room (구역)
        L5: Discipline (공종 코드)
```

## 5. 3-Way 매핑 구조 검토

Mapper가 실제로 연결해야 하는 구조:

```
[작업일보 텍스트]       [WBS Activity]          [품셈 코드]
"철근 배근"    →   A-F02-B01-03-020-022   →   C-6-2-3
(disc: 건축)     (건축-2층-B1F-RC공사-철근-조립)  (현장조립, 2.2 ton/일)
```

**2단계 매핑 구조:**
1. 작업일보 텍스트 + 공종 → WBS Activity 코드 (의미 기반 검색)
2. WBS Activity 코드 → 품셈 코드 (사전 정의 매핑 테이블)

**현실적 판단:** 2단계 완전 자동 매핑보다, **"공종 + 작업 카테고리 → 품셈 코드" 직접 매핑**이 더 간단하고 안정적이다.

```
작업일보 (공종=건축, 작업내용="철근 배근") 
  → Mapper: 건축+철근 → 품셈 C-6-2-3 직접 매핑
  → WBS 코드는 부가 정보로 함께 매핑 (별도 룩업 테이블)
```

## 6. 설비·전기 공종 매핑 가능성

### 설비 (H)
- 작업내용: "1F 공조배관 설치 FL4,400", "3F Exh.Duct 설치" 등
- **층+위치 정보가 혼재** (파싱 시 분리 필요)
- 공조배관 → 기계설비 품셈(M-x-x), Duct → 기계설비 품셈
- 규격(관경, 덕트 크기)에 따라 생산성 다름 → WBS에서 규격 파악 필요

### 전기 (E)
- 작업내용: "Cable Tray 설치", "Cable 포설(고압, 저압)", "분전반 설치"
- 비교적 표준화된 명칭 → 전기 품셈(E-x-x) 매핑 가능성 높음
- "Cable 포설(저압+가설)" 처럼 복합 표현은 분리 필요

### UT/소방 공종
- UT(P): "UT배관공사" 등 → 배관 규격별 품셈
- 소방(F): 소방 설비·전기로 별도 분리되어 있음

**설비·전기는 규격(관경, 케이블 굵기 등)이 생산성 결정 요인**이라, 작업일보에 규격이 없으면 Forecaster 계산 부정확. PoC에서는 건축 RC 공종이 가장 단순하고 안전하다.

## 7. 핵심 리스크 및 발견

### R1: FAB 특화 작업의 품셈 공백 (높음)

건축 307건 중 추정 **30~40%가 반도체 FAB 특화 작업** (System Ceiling, CMP, S/C 작업 등)으로 국가 표준품셈에 코드가 없다. 이 작업들은:

- Mapper가 `requires_review: true` 플래그를 붙여야 함
- H-i-L 1에서 사용자가 직접 카테고리/생산성 기준 지정
- corrections.json에 누적 저장하여 반복 개선

PoC에서 이 비율이 높으면 H-i-L 부담이 커진다. **PoC 공종을 "건축 RC"(철근+거푸집+콘크리트)로 좁히면 이 문제 회피 가능.**

### R2: 품셈 생산성 기준값 선정 필요 (중간)

각 품셈 코드의 생산성이 조건별로 다중값이기 때문에 Forecaster가 사용할 **단일 기준값** 을 사람이 한번 결정해야 한다.

**권고:** Week 1에서 선택한 2~3개 공종에 대해 아래 형태로 `poom_sem_ref.json`을 수동 작성:

```json
{
  "철근_현장조립": {
    "poom_sem_code": "C-6-2-3",
    "unit": "ton",
    "std_productivity": 2.2,
    "basis": "Ⅰ-2 기준 (M15X FAB 복잡도 중간 가정)",
    "note": "규격 Ⅰ-1(3.4)~Ⅱ-2(1.1) 범위에서 현장 담당자 확인 필요"
  },
  "거푸집_합판": {
    "poom_sem_code": "C-6-3-1",
    "unit": "m2",
    "std_productivity": 30,
    "basis": "복잡 기준 (FAB 구조물 특성 반영)",
    "note": "알루미늄폼 사용 시 C-6-3-7으로 교체 필요"
  },
  "콘크리트_펌프타설_철근": {
    "poom_sem_code": "C-6-1-4",
    "unit": "m3",
    "std_productivity": 125,
    "basis": "슬럼프 8~12cm, 철근구조물 기준",
    "note": "조 편성(품셈 기준 25명) 대비 작업일보 인원 비율 보정 필요"
  }
}
```

### R3: 인원 단위 기준 불일치 (높음)

> **가장 중요한 구조적 문제**

| 구분 | 내용 |
|------|------|
| 실행계획서 가정 | `실측 생산성 = 당일 물량 ÷ 당일 투입 인원` |
| 품셈 기준 | `n명으로 구성된 조가 하루에 처리하는 시공량 (조 단위 생산성)` |
| 작업일보 데이터 | 협력사 전체 투입 인원 (조 단위가 아닌 총원) |

예시: 남웅건설이 철근 배근에 42명 투입, 금일 실적 15 ton → 실측 생산성 = 0.36 ton/인
품셈 C-6-2-3 기준 1.1~3.4 ton/일(조) → 조 편성을 모르면 비교 불가

**해결 방안:** Forecaster를 "인원당 생산성" 비교가 아닌, **"조 수 환산 후 예상 완료일 계산"** 방식으로 재설계 검토 필요. 또는 품셈 생산성을 "1인당 기준값"으로 환산한 poom_sem_ref.json을 별도 작성.

### R4: 금일실적 None 처리 (낮음)

데이터 중 금일실적이 None인 경우가 많음. "작업 없음"인지 "미입력"인지 구분 로직 필요.
`금일실적 = None`이고 `Forecast = 0`인 경우 Forecaster에서 "당일 공정 없음"으로 처리.

## 8. PoC 공종 선택 권고

실행계획서가 제안한 "철근·거푸집·콘크리트"는 **현실적으로 최선의 선택**이다.

| 거푸집 | ✅ 높음 | C-6-3-1 존재 | m² ✅ | **선정** |

## 9. Mapper 설계 조정 사항

실행계획서 Mapper 설계에서 아래 사항을 보완:

### 변경 1: 2단계 매핑 → 1단계 직접 매핑으로 단순화

```
현행(계획서): 작업텍스트 → WBS Activity → 품셈 코드
권고:         작업텍스트 + 공종 → 품셈 코드 + WBS 코드 (동시)
```

이유: WBS는 4,330개 Activity가 있어서 작업일보 텍스트에서 특정 WBS Activity로 정확히 연결하기 어려움. 대신 품셈 코드는 공종별로 20~40개 수준이어서 시멘틱 검색 정확도가 훨씬 높다.

### 변경 2: 품셈 직접 생산성 사용 대신 poom_sem_ref.json 참조

Mapper가 품셈 코드를 연결하면, Forecaster는 poom_sem_ref.json에서 **사람이 사전 확정한 단일 기준값**을 참조. (품셈 JSON을 직접 파싱하여 생산성을 추출하지 않음)

### 변경 3: FAB 특화 작업에 대한 fallback 카테고리 추가

매핑 불가(품셈 공백) 작업에 대해 "FAB_SPECIFIC" 카테고리를 추가하고, H-i-L에서 수동 생산성 지정 후 corrections.json에 저장.

## 10. 종합 판단

| 항목 | 판단 |
|------|------|
| Mapper 시멘틱 매핑 전반 | **가능** — 단, 대상 공종을 건축 RC로 좁히면 실현 가능성 대폭 향상 |
| 품셈 데이터 생산성 기준 | **존재하지만 단일값 아님** — poom_sem_ref.json 수동 작성 필요 (Week 1) |
| Forecaster 계산 로직 | **기본 구조 가능** — 단, "인원당 생산성 vs 품셈 조 기준" 매핑 방식 정의 필요 |
| FAB 특화 작업 처리 | H-i-L 1 + corrections.json으로 점진적 해결 가능 |
| PoC 2~3개 공종 선정 | **철근 + 거푸집 + 콘크리트** 조합이 데이터 품질·품셈 대응성 모두 최적 |
| 작업일보 Parser 난이도 | 통합 작업일보(시트4)는 이미 정리된 형태 → Parser보다 **직접 파싱**이 더 빠름 |

> 핵심 한 줄: **Mapper는 동작 가능하다. 단, 품셈 생산성 기준값을 Week 1에서 수동으로 정의하지 않으면 Forecaster가 작동하지 않는다.**

BG · Background

과제의 본질 —
현장의 일을 재정립한다

이 과제는 단순히 현장의 보고 업무를 줄이는 자동화가 아닙니다. 현장 엔지니어가 수행하는 업무 중 AI로 대체 가능한 Middle Office 레이어를 제거하고, 그 인력을 Front Office 본연의 역할(공정 판단·발주처 협상·리스크 실행)로 재배치함으로써 조직의 일하는 방식을 구조적으로 전환합니다.

02 · Architecture

통합 AI 파이프라인 구조

과제 A(데이터 수집·보고 자동화)와 과제 B(공기 예측)는 동일한 데이터 원천에서 출발하는 연속 파이프라인입니다. Step 3의 구조화 DB가 Step 4의 학습 원천이 되어 데이터가 쌓일수록 예측 정확도가 향상되는 선순환을 만듭니다.

5-STEP CONTINUOUS PIPELINE
STEP 01
데이터 수집
이메일·카카오톡·SNS 자동 수신, 엑셀·텍스트 파싱, 표준 스키마 DB 적재
과제 A
STEP 02
정합성 검증
이상치 자동 감지, 전일 대비 급변 탐지, 담당자 알림 발송
과제 A
STEP 03
Semantic Mapping + 보고서 생성
비정형 텍스트 → 공정표 자동 분류, Daily·Weekly Report 자동 생성, 발주처 자동 발송
과제 A
STEP 04
공기 리스크 탐지
누적 실적 추세 분석, 잔여 공기 내 물량 소화 가능 여부 판단, D-14 자동 알림
과제 B
STEP 05
만회 시나리오 제시
인원 증가 / 야간작업 / 공종 조정 3안 자동 생성, Critical Path 재조정, Catch-up Plan 초안
과제 B
수집·보고 자동화 (과제 A)
공기 예측·만회 (과제 B)
Step 3 구조화 DB → Step 4 학습 데이터: 연속 선순환
연결점 ①
Output이 곧 다음 Input
과제 B가 필요한 "협력사별 일별 물량·인원 실적"이 과제 A의 산출물과 정확히 일치. 현재는 B 담당자가 A 보고서를 다시 수기로 읽어 작업 시작.
연결점 ②
A가 B의 예측 품질 결정
A로 표준 구조화 DB가 쌓이면 B의 시계열 예측 정확도가 향상. 현재 비정형 엑셀은 B의 학습 데이터로 활용 불가.
연결점 ③
보고 속도가 예측 가치 결정
B가 D-14 위험을 탐지해도 A의 보고서 완성에 3일 걸리면 D-11 경보가 됨. A·B 동시 자동화로 Same-day 처리.

3단계 AI 처리 흐름 (데이터 → 인사이트)
Stage 1
Semantic Mapping
비정형 작업일보 텍스트를 LLM이 문맥 해석 → 공정표·실행내역 항목에 자동 분류·할당. 현재 담당자가 수작업으로 하는 가장 많은 시간을 소모하는 단계.
Stage 2
Reasoning (CPI/SPI)
일단위 공정률·생산성 지표(CPI/SPI) 자동 산출. 표준 품셈 대비 실적 비교, 효율 저하 구간 원인 추론. 예산관리팀 90h/월 수작업 대체.
Stage 3

기술 구현 — LangGraph 기반
Multi-Agent 아키텍처

CPIA는 단일 LLM 호출이 아닌 5개 전문 Agent가 상태를 공유하며 협력하는 구조입니다. 파이프라인 중간에 PM이 이상 데이터를 직접 검토하는 Human-in-the-Loop 구간이 필수적으로 존재하며, 이를 네이티브로 지원하는 LangGraph StateGraph를 채택합니다.

LangChain vs LangGraph — 왜 LangGraph인가
비교 항목 LangChain LangGraph ✓ 채택
실행 구조 선형 체인 — A→B→C 순차 실행. 분기·반복 불가. ✓ StateGraph — 조건 분기·사이클·병렬 실행 모두 지원.
Human-in-the-Loop ✗ 네이티브 미지원. 체인 중단 후 상태 보존 불가. ✓ interrupt() — 파이프라인 일시정지, 상태 저장, PM 승인 후 재개.
Multi-Agent 단일 AgentExecutor 기반. Agent 간 상태 공유 어려움. ✓ CPIAState 공유로 5개 Agent가 동일 컨텍스트 접근.
조건부 라우팅 if/else 직접 구현. 파이프라인 구조 외부에 존재. ✓ add_conditional_edges() — 이상치 탐지 시 자동 분기.
장애 복원 체인 실패 시 처음부터 재실행. ✓ PostgresSaver — 단계별 상태 저장, 장애 지점부터 재개.
적합 Use Case 단일 Agent RAG, 문서 Q&A, 단순 Tool 호출. ✓ Human 개입 포함 복잡한 Multi-Agent 오케스트레이션.

CPIAState — 공유 상태 및 그래프 조립
# 모든 Agent가 공유하는 단일 상태 객체 from langgraph.graph import StateGraph, START, END from typing import TypedDict, Literal from langgraph.checkpoint.postgres import PostgresSaver class CPIAState(TypedDict): date: str # 처리 기준일 raw_reports: list[dict] # Collector: BP 원본 작업일보 structured_data:list[dict] # Parser: WBS 매핑 완료 데이터 anomalies: list[dict] # Validator: 감지된 이상치 목록 human_approved: bool # Human Review: PM 승인 여부 daily_report: str # Reporter: 생성된 보고서 forecast: dict # Forecaster: D-14 리스크 예측 결과 alerts: list[str] # 발송된 알림 메시지 # 이상치 여부에 따라 human_review 또는 reporter로 분기 def route_after_validation(state: CPIAState) -> Literal["human_review", "reporter"]: return "human_review" if state["anomalies"] else "reporter" # Human-in-the-Loop: interrupt()로 파이프라인 일시정지, 상태 보존 def human_review_node(state: CPIAState): from langgraph.types import interrupt interrupt({"anomalies": state["anomalies"], "action": "PM 검토 요청"}) return {"human_approved": True} # Reporter + Forecaster 병렬 실행 (Send API) from langgraph.types import Send def parallel_dispatch(state: CPIAState): return [Send("reporter", state), Send("forecaster", state)] # 그래프 조립 graph = StateGraph(CPIAState) graph.add_node("collector", collector_node) graph.add_node("parser", parser_node) graph.add_node("validator", validator_node) graph.add_node("human_review",human_review_node) graph.add_node("reporter", reporter_node) graph.add_node("forecaster", forecaster_node) graph.add_edge(START, "collector") graph.add_edge("collector", "parser") graph.add_edge("parser", "validator") graph.add_conditional_edges("validator", route_after_validation) graph.add_edge("human_review", "reporter") graph.add_conditional_edges("reporter", parallel_dispatch) graph.add_edge("forecaster", END) app = graph.compile(checkpointer=PostgresSaver.from_conn_string(DB_URL))
핵심 설계 원칙
원칙 ①
Human-in-the-Loop 보장
이상치 탐지 시 interrupt()로 파이프라인이 일시정지됩니다. PM이 모바일 알림으로 검토·승인하면 중단 지점부터 재개. AI가 의심 데이터를 자동 통과시키지 않습니다.
원칙 ②
장애 내성 및 복원
PostgresSaver가 각 노드 완료 시 상태를 DB에 저장합니다. Reporter 실패 시 Collector부터 재실행하지 않고 Reporter 직전 상태에서 재개. 현장 네트워크 불안정에 대응.
원칙 ③
모델 최적화 배치
속도·비용 균형이 중요한 Parser·Reporter는 Claude Sonnet 4.6, 복잡한 다단계 시나리오 추론이 필요한 Forecaster는 Claude Opus 4.7을 사용합니다.

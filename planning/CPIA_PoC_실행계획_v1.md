# CPIA PoC 실행계획

> **개인과제 | 2026년 5~6월 | 조형준 프로**
> 기획서 `design/CPIA_기획서_v6.md` 기반 실증 계획

---

## 이 문서의 목적

한 달 안에 "**Collector → Parser → Mapper → Reporter → Forecaster → Optimizer → Dashboard, 전체 파이프라인이 실제로 돌아간다**"는 것을 경영진 앞에서 라이브로 보여주는 것.

> **핵심 전략:** 공종 범위를 좁히되 전체 스토리를 완성한다.
> "모든 공종을 처리하지만 보고서 생성까지만" 보다
> "2~3개 공종이지만 생산성 분석 + 자원 재배치 최적화 + 대시보드까지 전부" 가 경영진에게 훨씬 강하게 전달됩니다.

## 1. PoC 범위 결정

### 포함 범위

| 구분 | 내용 |
|------|------|
| **대상 현장** | Y-1 Ph-1 OBL 단일 현장 |
| **대상 공종** | **2~3개 공종 선택 집중** (철근·거푸집·콘크리트 등 물량 데이터가 명확한 공종) |
| **구현 Agent** | **6개:** Collector → Parser → Mapper [H-i-L 1] → Reporter → Forecaster [H-i-L 2] → Optimizer |
| **입력 데이터** | 샘플 작업일보 5~10개 + **품셈 기준 생산성 데이터** + 잔여 계획 물량·완료일 (공정표) |
| **출력물** | 자동 생성 통합 Daily Report (사내 + 발주처용) + **경영진 대시보드 (Streamlit)** |
| **Human-in-the-Loop** | **H-i-L 1 (Mapper):** 매핑 검증 + 사용자 수정 피드백 루프 / **H-i-L 2 (Forecaster):** 최적화 공종 선택·승인. Week 3: 터미널, Week 4: 대시보드 버튼 |

### 제외 범위

| 제외 항목 | 이유 |
|----------|------|
| 6개 현장 확산 | 1개 현장 완성 후 확산은 반복 작업 — PoC 이후 |
| 이메일·카카오톡 실제 연동 | 보안 승인 절차 시간 소요 — 파일 드롭 방식으로 대체 |
| CPI 기반 비용 분석 | AC(실제 비용) 데이터가 작업일보에 없음 — SPI(생산성) 기반으로 구현, CPI는 Phase 2에서 비용 데이터 연동 후 추가 |
| Optimizer 자원 재배치 실행 | Optimizer는 최적 배분을 제안까지만 — 실제 인원 이동·발령 등 실행은 PM 판단 영역 |
| 전체 공종 처리 | 2~3개 공종만으로도 파이프라인 전체를 보여줄 수 있음 |

### 핵심 증명 명제

> "선택한 공종의 작업일보를 넣으면, AI가 공정표·품셈 분류에 자동으로 매핑하고(Mapper),
> 전체 협력사의 작업일보를 통합 보고서로 생성하며(Reporter),
> 품셈 기준 현재 생산성으로 예상 완료일을 산출하고(Forecaster),
> PM이 선택한 공정에 한해 내부 자원 재배치로 공기를 단축할 수 있는 최적 배분을 제안한다(Optimizer).
> 경영진은 6개 현장 현황 대시보드에서 현재 상태와 구체적 액션을 한 화면으로 본다."

## 2. 제작 방식

### 기본 방침

**"단순하게, 동작하게, 경영진이 이해하게"**

- 로컬 Python 환경에서 실행 가능한 수준으로 구현 (복잡한 인프라 불필요)
- Forecaster는 가상 히스토리 데이터로 흐름을 증명 — 예측 정확도는 PoC 목표가 아님
- 대시보드는 코드보다 **화면이 설득**한다는 원칙으로 설계

### 기술 선택

| 결정 사항 | 선택 | 이유 |
|----------|------|------|
| Agent 프레임워크 | LangGraph | H-i-L interrupt·조건 분기·병렬 실행이 핵심 |
| LLM 모델 | Claude Sonnet 4.6 (Parser·Reporter) / Opus 4.7 (Forecaster) | 기획서 설계와 동일 |
| 입력 방식 | 지정 폴더에 파일 드롭 | 이메일 연동 대신 — 개념 증명에 충분 |
| 대시보드 | **Streamlit** | Python만으로 빠르게 웹 UI 구성 가능, 데모용으로 최적 |
| Forecaster·Optimizer 데이터 | 품셈 기준 생산성 + 오늘 실적 + 잔여 계획 물량 | 과거 데이터 불필요 — 오늘 데이터만으로 즉시 작동 |
| 실행 환경 | 개인 PC (로컬) | 사내 인프라 승인 전 단계에서 빠르게 검증 |

### 데모 시나리오 (경영진 시연 기준)


## 3. 사전 준비 사항

### A. 데이터 준비 (가장 중요한 선행과제)

| 필요 데이터 | 형태 | 확보 방법 | 비고 |
|------------|------|----------|------|
| 작업일보 샘플 5~10개 | Excel 또는 텍스트 | Y-1 현장 담당자 요청 (비식별화) | 못 받으면 가상 데이터로 대체 가능 |
| WBS 구조표 (공종 목록) | Excel | 현장 PM에게 공종·Activity 목록 요청 | **2~3개 공종만 선택하면 충분** |
| **품셈 기준 생산성** (공종별) | Excel 또는 PDF | 수령 예정 (`data/poom_sem/` 폴더) | **Forecaster·Optimizer 핵심 기준값** — 없으면 두 Agent 동작 불가 |
| **잔여 계획 물량 + 계획 완료일** (공종별) | Excel | 현장 PM 또는 공정 담당자 요청 | Forecaster 예상 완료일 계산에 필요 |
| Plan 공정률 기준값 | Excel | 공정 담당자에게 마일스톤 진도율 요청 | S-curve 표시용, 기준값만 있으면 됨 |

> **현실적 대안:** 작업일보를 못 받더라도 양식 구조 파악 후 가상 데이터로 대체 가능.
> 단, **품셈 데이터와 잔여 계획 물량은 대체 불가** — Forecaster·Optimizer의 계산 근거이므로 반드시 확보 필요.

### B. API 및 개발환경

| 항목 | 확인 사항 | 예상 비용 |
|------|----------|---------|
| Claude API Key | Anthropic 계정 발급 | PoC 기간 $20~50 예상 (Opus 4.7 포함, 개발·테스트 반복 고려) |
| Python 환경 | 3.11+ / LangGraph·anthropic·streamlit 설치 | 무료 |
| 사내 AI 인프라 | PoC는 로컬 PC로 가능, 본격 운영 시 필요 | 향후 IT 협의 |

### C. 현장 협조 요청

| 대상 | 요청 내용 | 소요 시간 |
|------|----------|---------|
| Y-1 현장 담당자 1명 | 작업일보 양식 확인, 보고서 샘플 검토 | 미팅 1~2회 (각 30분) |
| 공정 담당자 (선택) | 공종 선택 + 공정률 산출 기준 확인 | 미팅 1회 (30분) |

> 현장 협조는 데이터 제공보다 **"이 보고서가 실제로 쓸 만한가"** 피드백이 목적입니다.
> 1시간 투자로 데모 완성도가 크게 달라집니다.

## 4. 단계별 진행 계획 (4주)

### 전체 데이터 흐름 개요

각 Week는 아래 파이프라인에 한 레이어씩 쌓아가는 구조입니다.

```
[Week 2] 작업일보 파일 드롭
              ↓
         Collector  — 파일 감지, 텍스트 추출
              ↓  (원본 텍스트)
          Parser   — 비정형 텍스트 → 구조화 JSON  (Claude Sonnet 4.6)
              ↓

[Week 3]   Mapper  — 작업 내용 → WBS·품셈 의미 기반 매핑 (Claude Sonnet 4.6)
              ↓
          [H-i-L 1] — 매핑 검증 + 사용자 수정 (LangGraph interrupt)
              ↓  확정 매핑
        ┌────┴──────────────────────────┐
     Reporter                      Forecaster
   통합 보고서 생성 (Sonnet)          공종별 생산성 분석 (Opus)
   사내 + 발주처용                    품셈 기준 달성률 + 예상 완료일
   history.csv 업데이트              리스크 공종 목록
                                          ↓
                                     [H-i-L 2] — PM이 최적화 공종 선택
                                          ↓  선택 공종만
                                     Optimizer
                                   자원 재배치 최적화 (Opus)
                                   구체적 인원 조정 제안
                                          ↓
                                   [실행 의사결정] — PM 검토·승인
        └────────────────────────────────┘
             ↓

[Week 4]  Dashboard — 전체 현황(6개 현장) + Y-1 상세 + H-i-L 버튼  (Streamlit)
```

**공유 데이터 저장소 (파이프라인 단계 간 연결 매개체)**

```
data/
  history.csv          ← Reporter가 매일 쌓는 실적 누적 (Dashboard가 읽음)
  corrections.json     ← Mapper H-i-L 수정 내역 누적 — 피드백 루프 (Mapper가 참조)
  forecast.json        ← Forecaster 출력 저장 (Optimizer·Dashboard가 읽음)
  optimizer.json       ← Optimizer 출력 저장 (Dashboard가 읽음)
  mock_sites.json      ← 나머지 5개 현장 더미 데이터 (Dashboard Layer 1용)
  poom_sem/            ← 품셈 기준 생산성 데이터 (Forecaster·Optimizer 참조)
output/
  reports/YYYYMMDD.md  ← Reporter가 생성하는 일일 보고서
input/
  YYYYMMDD/            ← Collector가 감시하는 작업일보 드롭 폴더
```

### Week 1 — 기반 구축

**목표:** 개발 환경 + 데이터 구조 설계 + 샘플 데이터 확보

#### 이번 주에 결정해야 할 것들

**① 대상 공종 선정 기준**

물량 단위가 숫자로 명확히 나오는 공종을 우선 선택합니다.
예: 철근(ton), 거푸집(m²), 콘크리트(m³) — 일일 변동이 있어서 이상치가 의미 있는 공종.
현장 담당자에게 "작업일보에서 물량을 가장 많이 적는 공종 2~3개"를 물어보는 게 가장 빠릅니다.

**② JSON 데이터 스키마 확정**

Parser 출력, DB 저장, Dashboard 표시까지 모든 단계가 이 구조를 공유합니다.
Week 1에서 확정해두지 않으면 나중에 전 단계를 수정해야 합니다.

```
[Parser 출력 JSON 스키마]
{
  "date": "2026-06-01",
  "bp_name": "협력사명",
  "activities": [
    {
      "wbs_code": "RC-001",
      "trade": "철근",
      "workers": 42,
      "quantity": 230,
      "unit": "ton",
      "progress_rate": 34.2,
      "cumulative_rate": 68.5
    }
  ]
}
```

**③ 품셈 데이터 구조화 및 Forecaster 계산 로직 설계**

수령한 품셈 데이터를 Forecaster가 참조할 수 있는 형태로 구조화합니다.
가상 히스토리 데이터는 **더 이상 필요 없습니다** — 오늘 실적 + 품셈 기준만으로 즉시 작동합니다.

```
[품셈 기준 생산성 구조 예시]  →  data/poom_sem/ 폴더에 저장
{
  "RC-001": { "trade": "철근 가공·조립", "unit": "ton", "std_productivity": 2.30 },
  "RC-002": { "trade": "거푸집 설치",   "unit": "m²",  "std_productivity": 18.5 },
  "RC-003": { "trade": "콘크리트 타설", "unit": "m³",  "std_productivity": 12.0 }
}

[Forecaster 계산 로직]
실측 생산성   = 당일 물량 ÷ 당일 투입 인원
품셈 달성률   = 실측 생산성 ÷ 품셈 기준 생산성 × 100%
예상 완료일   = 오늘 + (잔여 계획 물량 ÷ 실측 일일 생산량)
지연/여유     = 계획 완료일 − 예상 완료일
```

#### 진행 체크리스트

- [ ] 개발 환경 구성 (Python 3.11, LangGraph, anthropic, streamlit, openpyxl 설치·동작 확인)
- [ ] 현장 담당자에게 작업일보 샘플 요청 (못 받으면 양식 구조 파악 후 가상 데이터 생성)
- [ ] 대상 공종 2~3개 확정 + JSON 스키마 확정
- [ ] 가상 작업일보 샘플 5개 생성 (확정된 공종·양식 기준)
- [ ] 품셈 데이터 수령 후 `data/poom_sem/` 에 구조화 저장 (공종별 표준 생산성 JSON)
- [ ] 잔여 계획 물량·계획 완료일 확보 (공종별, 공정표에서 추출)
- [ ] **6개 현장 더미 데이터 JSON 생성** (`data/mock_sites.json`) — 대시보드 전체 현황 뷰 용도
  - Y-1 OBL 외 5개 현장의 공정률·D-14 리스크·이상치 건수를 사전 설정

### Week 2 — Collector + Parser

**목표:** "파일을 넣으면 구조화 JSON이 나온다"

#### Collector 작동 방식

| 항목 | 내용 |
|------|------|
| 기능 | 지정 폴더(`input/YYYYMMDD/`)를 감시하여 새 파일을 감지하고 텍스트를 추출 |
| 입력 | 작업일보 파일 (Excel `.xlsx` 또는 텍스트 `.txt`) |
| 처리 | Excel: `openpyxl`로 시트 전체 셀 텍스트 추출 / 텍스트: 직접 읽기 |
| 출력 | 파일별 원본 텍스트 문자열 → Parser로 전달 |
| 필요 데이터 | 샘플 작업일보 5개 |

#### Parser 작동 방식

| 항목 | 내용 |
|------|------|
| 기능 | 비정형 텍스트에서 공종별 [인원·물량·진도율]을 추출하여 JSON으로 변환 |
| 입력 | Collector의 원본 텍스트 + WBS 구조표 (프롬프트에 포함) |
| 처리 | Claude Sonnet 4.6 호출. WBS 구조를 프롬프트에 명시하여 매핑 정확도 확보 |
| 출력 | 구조화 JSON (Week 1에서 확정한 스키마 기준) |
| 필요 데이터 | WBS 구조표 (공종 코드·명칭·단위), 샘플 작업일보 5개 |

**Parser 프롬프트 핵심 구조:**
```
당신은 건설 현장 공정 데이터 추출 전문가입니다.
아래 WBS 공종 목록을 참고하여, 작업일보 원문에서
각 공종의 [투입 인원, 당일 물량, 누적 진도율]을 JSON으로 추출하세요.
공종명이 정확히 일치하지 않으면 가장 유사한 WBS 코드로 매핑하세요.

[WBS 공종 목록]
RC-001: 철근 (단위: ton)
RC-002: 거푸집 (단위: m²)
RC-003: 콘크리트 타설 (단위: m³)

[작업일보 원문]
{raw_text}

[출력 형식]
{"bp_name": ..., "activities": [{"wbs_code": ..., "trade": ..., ...}]}
```

**정확도 기준:** 샘플 5개 중 4개 이상에서 WBS 매핑 정상 (누락·오매핑 없음)

### Week 3 — Mapper + H-i-L 1 + Reporter + Forecaster + H-i-L 2 + Optimizer

**목표:** "매핑 검증 → 통합 보고서 생성 → 공기 리스크 탐지 + 최적화 공종 선택 → 재배치 제안, 전 Agent가 한 번에 돌아간다"

#### Mapper 작동 방식

| 항목 | 내용 |
|------|------|
| 기능 | 작업일보의 작업 내용 기술을 공정표 WBS 코드 및 품셈 분류에 의미 기반으로 매핑 |
| 입력 | Parser의 구조화 JSON + WBS 구조표 + 품셈 분류 목록 |
| 처리 | Claude Sonnet 4.6 호출. 각 Activity의 작업 내용 텍스트를 WBS 코드·품셈 카테고리에 의미 기반으로 매핑. 확신도 낮은 항목은 별도 플래그 처리 |
| 출력 | 매핑 완료 JSON (wbs_code·poom_sem_code 확정) + 불확실 항목 목록 (H-i-L 대상) |
| 필요 데이터 | WBS 구조표, 품셈 분류 목록 |

**Mapper 프롬프트 핵심 구조:**
```
당신은 건설 공정 매핑 전문가입니다.
아래 WBS 공종 목록과 품셈 분류 목록을 참고하여,
작업일보의 각 작업 내용 기술을 가장 적합한 WBS 코드와 품셈 카테고리에 매핑하세요.
매핑 확신도(0~1)를 함께 반환하고, 0.7 미만인 항목은 requires_review: true로 표시하세요.
이전 수정 내역(corrections.json)이 있으면 우선 참조하세요.

[WBS 공종 목록] ...
[품셈 분류 목록] ...
[이전 수정 내역] {corrections_history}
[작업일보 Activities] {parsed_activities}
```

#### H-i-L 1 (Mapper) 작동 방식

| 항목 | 내용 |
|------|------|
| 기능 | 매핑 결과를 담당자가 검증하고, 오매핑 항목을 수정하여 정확도 피드백 루프 구성 |
| 입력 | Mapper의 전체 매핑 결과 + 불확실 항목 목록 (requires_review: true) |
| 처리 | LangGraph `interrupt()` 호출 → 매핑 결과 전체 표시 (확신도 낮은 항목 강조) → 담당자 수정 입력 대기 |
| 출력 | 확정 매핑 JSON + 수정 내역 → `data/corrections.json`에 누적 저장 |
| 구현 | Week 3: 터미널 출력 + 수정 입력 / Week 4: 대시보드 UI로 교체 |

> **피드백 루프:** 담당자가 수정한 매핑 내역은 `corrections.json`에 누적.
> 이후 실행 시 동일 작업 내용이 나오면 Mapper가 corrections.json을 먼저 참조하여 자동 확정 처리.
> 반복할수록 H-i-L 개입 빈도가 줄어드는 구조.

#### Reporter 작동 방식

| 항목 | 내용 |
|------|------|
| 기능 | 전체 협력사의 작업일보를 통합한 Daily Report를 생성 — **사내 현장담당자 제공 + 발주처 보고용으로 동시 활용** |
| 입력 | Mapper의 확정 매핑 JSON + history.csv의 Plan 기준값 |
| 처리 | Claude Sonnet 4.6으로 보고서 마크다운 생성 (공정률 요약·BP별 현황·공종별 매핑 결과 포함) |
| 출력 | `output/reports/YYYYMMDD.md` + history.csv 업데이트 (오늘 실적 행 추가) |
| 필요 데이터 | Plan 공정률 기준값 (S-curve 마일스톤), BP 전체 목록 |

#### Forecaster 작동 방식 (Reporter와 병렬 실행)

| 항목 | 내용 |
|------|------|
| 기능 | 공종별·BP별 현재 생산성을 품셈 기준과 비교하여 예상 완료일 산출 및 SPI 계산, 리스크 공종 목록 생성 |
| 입력 | 오늘 Mapper 확정 JSON (인원·물량) + 품셈 기준 생산성 (`data/poom_sem/`) + 잔여 계획 물량·계획 완료일 |
| 처리 | **계산:** 실측 생산성 = 당일 물량 ÷ 투입 인원 → 품셈 달성률 → 예상 완료일 → 지연/여유일 산출. **LLM 해석:** Claude Opus 4.7에게 공종별 달성률 패턴을 주고 "어떤 공종이 왜 저하되고 있는가" 추론 |
| 출력 | `data/forecast.json` — 공종별 {품셈 달성률, 예상 완료일, 지연일, SPI, 저하 원인 추론} + **리스크 공종 목록** (H-i-L 2 입력) |
| 필요 데이터 | 품셈 기준 생산성, 잔여 계획 물량, 계획 완료일 (과거 데이터 불필요) |

#### H-i-L 2 (Forecaster → Optimizer) 작동 방식

| 항목 | 내용 |
|------|------|
| 기능 | Forecaster가 탐지한 리스크 공종 중 실제로 Optimizer에 최적화를 의뢰할 대상을 PM이 선택·승인 |
| 입력 | Forecaster의 리스크 공종 목록 + 공종별 지연 상황 요약 |
| 처리 | LangGraph `interrupt()` 호출 → 리스크 공종 목록 + 지연 원인 추론 표시 → PM이 최적화 의뢰 대상 선택. **선택하지 않은 공종은 Optimizer 스킵** (환경 변수·현장 상황상 생산성 계산이 부정확할 수 있는 공종을 PM 판단으로 제외) |
| 출력 | 최적화 의뢰 확정 공종 목록 → Optimizer로 전달 |
| 구현 | Week 3: 터미널 체크 선택 / Week 4: 대시보드 체크박스로 교체 |

#### Optimizer 작동 방식 (H-i-L 2 승인 후 실행)

| 항목 | 내용 |
|------|------|
| 기능 | PM이 선택한 공종에 한해 내부 자원 재배치로 지연을 만회할 수 있는 최적 배분을 제안 |
| 입력 | `data/forecast.json` + H-i-L 2 확정 공종 목록 + 오늘 공종별·BP별 투입 인원 현황 + 품셈 기준 생산성 |
| 처리 | Claude Opus 4.7에게 "선택된 공종의 지연을 추가 채용 없이 내부 재배치만으로 만회할 수 있는 구체적 인원 이동 계획을 제시하라. 재배치로 불가능한 경우 추가 투입 인원 수를 계산하라" |
| 출력 | `data/optimizer.json` — {재배치 가능 인원, 이동 경로(A공종→B공종 N명), 예상 만회 일수, 추가 투입 필요 시 인원 수} |
| 필요 데이터 | forecast.json, 오늘 공종별 투입 인원, 품셈 기준 생산성 |

**Optimizer 출력 예시:**
```
[PM 선택 공종: 철근]
철근 공종: 현재 생산성 74%, 6일 지연 예상
거푸집 공종: 현재 생산성 108%, 인원 여유 있음

→ 재배치 제안:
   거푸집 → 철근: 8명 이동
   이동 후 철근 생산량: 42 → 50명 기준 85.0 ton/일
   예상 완료일: 현재 D+26 → D+22 (4일 단축)
   잔여 지연: 2일 (추가 투입 또는 야간 작업 필요)
```

**[실행 의사결정 지점]**
> Optimizer 제안 검토 후 PM이 실행 여부를 결정합니다.
> 제안 수락 시 시스템이 조치 지시 내용을 자동 정리하여 담당자에게 전달합니다.
> 이 단계는 H-i-L이 아닌 PM의 자율 판단 영역입니다 — 시스템은 제안만 하고 실행은 사람이 결정합니다.

#### 진행 체크리스트

- [ ] Mapper 구현: WBS·품셈 의미 기반 매핑 (Sonnet 4.6) + 확신도 플래그 처리 + corrections.json 참조
- [ ] H-i-L 1 구현: LangGraph interrupt + 매핑 결과 표시 + 사용자 수정 입력 + corrections.json 누적 저장
- [ ] Reporter 구현: Sonnet 4.6 통합 보고서 생성 (사내 + 발주처용) + history.csv 업데이트

**Week 3 체크포인트:** 샘플 드롭 → Mapper 매핑 검증 (H-i-L 1) → 통합 보고서 자동 생성 → 리스크 공종 선택 (H-i-L 2) → Optimizer 재배치 제안이 터미널에 출력된다.

| 매핑 이력 | Mapper 매핑 결과 + 수정 내역 테이블 | corrections.json (파이프라인 연동) |
| D-14 상세 | 예상 지연일 + 공종별 생산성·만회 시나리오 | forecast.json (파이프라인 연동) |
| H-i-L 승인 | H-i-L 1 (매핑 검증) + H-i-L 2 (최적화 공종 선택) 버튼 | LangGraph interrupt 연동 |
| Daily Report | 날짜별 보고서 링크 | output/reports/ 폴더 |

나머지 5개 현장 클릭 시에도 Layer 2 화면이 열리지만, mock_sites.json의 정적 데이터를 표시합니다.
(S-curve·이상치 이력 모두 사전 작성된 더미값)

**Dashboard ↔ Pipeline 연결 방식:**
```
Pipeline 실행 완료 (Y-1)
    ↓
Mapper    → corrections.json 업데이트
Reporter  → history.csv 업데이트
Forecaster → forecast.json 저장
Optimizer → optimizer.json 저장
    ↓
Dashboard → 파일 재읽기 → Layer 1 Y-1 카드 + Layer 2 상세 화면 자동 갱신

나머지 5개 현장 → mock_sites.json 고정값 (업데이트 없음)
```

#### 진행 체크리스트

- [ ] **Layer 1 구현:** 6개 현장 현황 카드 (공정률·D-14·이상치·보고 상태)
  - Y-1: 파이프라인 연동 실데이터 / 나머지 5개: mock_sites.json 더미값
- [ ] **Layer 2 구현:** Y-1 현장 상세 화면 (S-curve·이상치·D-14 상세·보고서 링크)
- [ ] H-i-L 승인 버튼 구현 (Week 3 터미널 방식 → Layer 2 화면 내 버튼으로 교체)
- [ ] 파이프라인 실행 결과 → Layer 1·2 자동 갱신 연결 확인
- [ ] End-to-End 통합 테스트: 파일 드롭 → Layer 1 Y-1 카드 갱신까지 전체 흐름 확인
- [ ] 데모 시나리오 리허설: Layer 1(전체 현황) → Y-1 클릭 → Layer 2(상세) → 파이프라인 실행 → 갱신 순서로 5분 시연
- [ ] AS-IS vs TO-BE 비교 슬라이드 1장 (수작업 3시간 → AI 5분, 6개 현장 동시 관제)
- [ ] 결과 문서화: 무엇이 됐고, 실운영 전환에 필요한 것은 무엇인지

**Week 4 체크포인트:** Layer 1(6개 현장 전체 현황) + Layer 2(Y-1 실데이터 상세)가 경영진 앞에서 라이브 시연 가능한 상태.

## 5. PoC 성공 기준

경영진 시연에서 **아래 4가지를 실제로 보여줄 수 있으면** 성공입니다.

| # | 성공 기준 | 검증 방법 |
|---|----------|---------|
| 1 | 작업일보 파일 투입 → 통합 Daily Report 자동 생성 (사내 + 발주처용) | 라이브 실행 |
| 2 | Mapper: 공종·품셈 의미 기반 자동 매핑 + H-i-L 1 검증·수정 (피드백 루프 확인) | 매핑 결과 + corrections.json 저장 데모 |
| 3 | Forecaster: 품셈 기준 공종별 생산성 달성률 + 예상 완료일 + H-i-L 2 최적화 공종 선택 | Forecaster 출력 + PM 선택 시연 |
| 4 | Optimizer: PM이 선택한 공종 기준 내부 자원 재배치 구체적 인원 이동 계획 출력 | Optimizer 출력 화면 |
| 5 | 6개 현장 전체 현황(Layer 1) → Y-1 상세·파이프라인 연동(Layer 2) 대시보드 시연 | Streamlit 화면 시연 |

**처리 시간 목표:** 전체 파이프라인 5분 이내 (vs. 수작업 2~3시간)

> **PoC에서 검증하지 않아도 되는 것:**
> Forecaster 예측 정확도, 시스템 운영 안정성, 보안 적합성 — 이는 Phase 2 과제입니다.
> "이런 흐름으로 작동한다"는 것만 보여주면 됩니다.

## 6. 리스크 및 대응

| 리스크 | 발생 가능성 | 대응 방안 |
|--------|-----------|---------|
| 현장 데이터 수령 지연 | 높음 | Week 1부터 요청 시작, 안 오면 가상 데이터로 선행 개발 |
| 작업일보 양식이 너무 다양 | 중간 | 2~3개 공종·양식만 선택해서 집중, 나머지는 Phase 2에서 |
| Parser 정확도 부족 | 중간 | 프롬프트에 WBS 구조 명시적 포함, 선택 공종 좁혀서 집중 |
| Mapper 매핑 정확도 부족 | 중간 | 작업 내용 기술이 너무 다양하면 LLM 매핑이 불안정. 프롬프트에 작업 내용 예시를 충분히 포함하고, H-i-L 1에서 사용자 수정으로 커버. corrections.json 누적으로 반복 개선 |
| 품셈 데이터 수령 지연 | 높음 | 품셈 없으면 Forecaster·Optimizer 동작 불가 — 최우선 확보 필요. 지연 시 임시로 표준 생산성 수치를 인터넷 참고값으로 대체 |
| Optimizer 제안 품질 저하 | 중간 | 투입 인원 데이터 정확도에 의존. 작업일보에 인원이 명확히 기재되지 않으면 재배치 계산 부정확 — 선택 공종 인원 기재 여부 사전 확인 |
| H-i-L 2에서 PM이 모든 공종 최적화 요청 | 낮음 | 전체 공종 최적화 시 Optimizer 출력이 복잡해질 수 있음. PoC에서는 1~2개 공종으로 제한 권고 |
| 대시보드 개발 시간 부족 | 중간 | Week 4 초반부터 집중 — 문서화·리허설은 뒤로 밀고 대시보드 우선. 경영진 시연에서 대시보드는 필수 |
| 라이브 시연 중 API 오류·지연 | 중간 | 핵심 구간 사전 실행 결과 캡처 보유 (만약 API 오류 시 캡처 화면으로 진행), 시연 당일 API 상태 사전 점검 |
| 4주 내 전체 완성 불가 | 중간 | Mapper + Reporter + Forecaster (H-i-L 포함) + 대시보드 최소 구현(S-curve·D-14 지표만)까지가 최소 시연 단위. Optimizer·이력 기능은 이후 추가 |

# CPIA PoC 실행계획

> **개인과제 | 2026년 5~6월 | 조형준 프로**
> 기획서 `design/CPIA_기획서_v6.md` 기반 실증 계획

---

## 이 문서의 목적

한 달 안에 "**AI Agent가 작업일보를 받아 당일 보고서를 자동으로 만들어낸다**"는 것을 실제로 돌아가는 코드로 보여주는 것.

설명자료(PPT)가 아닌 **동작하는 데모**가 목표입니다.

---

## 1. PoC 범위 결정: 무엇을 증명할 것인가

전체 CPIA는 5개 Agent + 6개 현장을 대상으로 합니다.  
1개월 개인과제로 전부 구현하는 것은 현실적이지 않습니다.  
**가장 임팩트 있는 한 조각을 완성도 있게 증명**하는 것이 목표입니다.

### PoC 범위 (포함)

| 구분 | 내용 |
|------|------|
| **대상 현장** | Y-1 Ph-1 OBL 단일 현장 (6개 현장 중 최대 규모, 967h/월) |
| **구현 Agent** | Collector → Parser → Validator → Reporter (4개) |
| **입력 데이터** | 샘플 작업일보 5~10개 (Excel 또는 텍스트 형태) |
| **출력물** | 자동 생성 Daily Report (Markdown 또는 HTML) |
| **Human-in-the-Loop** | 이상치 감지 시 터미널 승인 프롬프트 (간이 구현) |

### PoC 범위 (제외)

| 제외 항목 | 이유 |
|----------|------|
| Forecaster Agent (D-14 탐지) | 최소 2개월치 누적 데이터 필요 — PoC에서는 데이터 없음 |
| 6개 현장 확산 | 1개 현장 완성 후 확산은 반복 작업 |
| 이메일·카카오톡 실제 연동 | 보안 승인 절차 시간 소요 — 파일 드롭 방식으로 대체 |
| 경영진 대시보드 UI | PoC 단계에서 불필요, 핵심은 파이프라인 자체 |

> **증명 명제:** "작업일보 파일 5개를 넣으면, 사람이 개입 없이 Daily Report가 생성된다.  
> 이상치가 있으면 알림이 오고, 확인 후 보고서가 발송된다."

## 2. 제작 방식

### 기본 방침

**"단순하게, 동작하게, 설명 가능하게"**

- 복잡한 인프라 구축 없이 **로컬 Python 환경에서 실행 가능**한 수준으로 구현
- 실제 현장에서 쓰는 파일 형식(Excel, 텍스트)을 그대로 입력으로 사용
- 코드보다 **결과물(보고서 샘플)** 이 더 잘 보이는 데모 구성

### 기술 선택 원칙

| 결정 사항 | 선택 | 이유 |
|----------|------|------|
| Agent 프레임워크 | LangGraph | 기획서에 명시된 대로, H-i-L 구현이 핵심 |
| LLM 모델 | Claude API (Sonnet 4.6) | Parser·Reporter에만 사용, 비용 최소화 |
| 입력 방식 | 지정 폴더에 파일 드롭 | 이메일 연동 대신 — 개념 증명에 충분 |
| 출력 형식 | Markdown 보고서 | 추후 PPT·메일 변환 용이 |
| 실행 환경 | 개인 PC (로컬) | 사내 인프라 승인 전 단계에서 빠르게 검증 |

### 데모 시나리오 (목표 화면)

```
[입력]
  작업일보_20260601_BP001.xlsx  ←── 실제 양식을 모방한 샘플
  작업일보_20260601_BP002.txt
  ...총 5개 파일

[CPIA 실행]
  Collector: 5개 파일 수집 완료
  Parser:    구조화 완료 (인원 42명, 물량 1,230m², 진도율 34.2%)
  Validator: ⚠️ 이상치 감지 — BP003 물량 전일 대비 +180% 초과
  [담당자 확인 필요] 계속하시겠습니까? (y/n):  y
  Reporter:  Daily Report 생성 완료

[출력]
  report_20260601.md
  → 공정률 요약, S-Curve 현황, BP별 투입 현황, 이상치 메모 포함
```

## 3. 사전 준비 사항

PoC 착수 전에 확보해야 할 것들입니다. **데이터 확보가 가장 중요한 선행과제**입니다.

### A. 데이터 준비 (가장 우선순위 높음)

| 필요 데이터 | 형태 | 확보 방법 | 담당 |
|------------|------|----------|------|
| 작업일보 샘플 5~10개 | Excel 또는 텍스트 | Y-1 현장 담당자에게 요청 (비식별화 또는 구조만) | 현장 협조 |
| WBS 구조표 | Excel | 현장 PM에게 공종·Activity 목록 요청 | 현장 협조 |
| Plan 공정률 곡선 | Excel 또는 P6 데이터 | 공정 담당자에게 마일스톤 및 계획 진도율 요청 | 현장 협조 |

> **데이터를 못 받는 경우:** 현장 담당자가 작성한 양식 구조를 파악한 뒤,  
> 동일 양식으로 가상 데이터를 직접 생성하는 것도 가능합니다.  
> (PoC 목적이라면 가상 데이터로도 개념 증명 가능)

### B. API 및 개발환경 접근

| 항목 | 확인 사항 | 비고 |
|------|----------|------|
| Claude API Key | Anthropic 계정에서 발급, 소액 비용 발생 | PoC 규모에서 월 $5~10 수준 예상 |
| Python 환경 | 3.11+ 권장, LangGraph·anthropic SDK 설치 | 개인 PC에서 가능 |
| 사내 AI 인프라 | PoC 이후 본격 운영 시 필요 — PoC 단계는 로컬 가능 | 향후 협의 사항 |

### C. 현장 협조 요청 (핵심)

데이터 제공 외에 **검토 협조**가 필요합니다.

| 협조 요청 대상 | 내용 | 시점 |
|-------------|------|------|
| Y-1 현장 담당자 1명 | 작업일보 양식 확인, 출력 보고서 샘플 검토 | Week 1~2 |
| 공정 담당자 (선택) | WBS 구조 및 공정률 산출 방식 확인 | Week 2 |

> 전일 투입을 요청하는 것이 아닙니다. 30분~1시간 미팅 1~2회로 충분합니다.  
> "이 양식이 맞냐", "이 보고서 형태가 현장에서 쓸 만 하냐" 확인이 목적입니다.

## 4. 단계별 진행 계획 (4주)

### Week 1 — 기반 구축 (환경 + 데이터)

**목표:** 개발 시작 가능한 상태 만들기

- [ ] 개발 환경 구성 (Python, LangGraph, Claude API 설치·테스트)
- [ ] 현장 담당자에게 작업일보 샘플 요청 및 수령
- [ ] WBS 구조 파악 (공종 분류 체계, Activity 명칭 패턴)
- [ ] 샘플 작업일보 5개 확보 또는 가상 데이터 생성
- [ ] LangGraph Hello World 수준 파이프라인 뼈대 구성

**Week 1 체크포인트:** 샘플 데이터가 있고, 파이프라인이 구조적으로 돌아간다.

---

### Week 2 — 핵심 파이프라인 구현 (Collector + Parser)

**목표:** "파일을 넣으면 구조화된 데이터가 나온다"

- [ ] Collector: 지정 폴더에서 파일 수집 + 형식별 텍스트 추출
- [ ] Parser: Claude Sonnet 4.6으로 비정형 텍스트 → WBS 매핑 JSON 변환
- [ ] Parser 정확도 검증: 5개 샘플 기준 WBS 매핑 정확도 확인 (목표 80%+)
- [ ] 현장 담당자에게 Parser 출력 결과 1차 검토 요청

**Week 2 체크포인트:** 샘플 5개를 넣었을 때 구조화 JSON이 생성된다.

---

### Week 3 — 완성 파이프라인 (Validator + Reporter + H-i-L)

**목표:** "이상치를 발견하고, 최종 보고서가 만들어진다"

- [ ] Validator: 통계 기반 이상치 감지 (전일 대비 ±30% 초과 Rule)
- [ ] Human-in-the-Loop: 이상치 발생 시 터미널 승인 프롬프트 구현
- [ ] Reporter: 승인 후 Daily Report 자동 생성 (Markdown 형태)
- [ ] 보고서 내용 구성: 공정률 요약 / BP별 투입 현황 / 이상치 메모 포함
- [ ] 전체 파이프라인 End-to-End 연결 및 통합 테스트

**Week 3 체크포인트:** 이상치 포함된 샘플 데이터로 전체 흐름이 동작한다.

---

### Week 4 — 데모 완성 및 정리

**목표:** "보여줄 수 있는 데모"와 "설명할 수 있는 결과"

- [ ] 데모 시나리오 스크립트 작성 (5분 분량)
- [ ] 보고서 출력 품질 개선 (현장 담당자 피드백 반영)
- [ ] "AS-IS vs TO-BE" 비교 자료 작성 (수작업 2~3h → AI 5분)
- [ ] 결과 정리: 무엇이 됐고, 무엇이 안 됐는지 솔직하게 기록
- [ ] 다음 단계(Forecaster 추가, 실제 이메일 연동) 요건 정의

**Week 4 체크포인트:** 데모 가능한 상태, 결과 문서화 완료.

## 5. PoC 성공 기준

발표 또는 데모에서 **아래 3가지를 보여줄 수 있으면** 성공입니다.

| # | 성공 기준 | 검증 방법 |
|---|----------|---------|
| 1 | 샘플 작업일보 5개를 넣으면 Daily Report가 자동 생성된다 | 실제 실행 데모 |
| 2 | 이상치가 포함된 데이터에서 알림이 발생하고 H-i-L이 작동한다 | 이상치 케이스 삽입 후 데모 |
| 3 | 전체 처리 시간이 5분 이내다 (vs. 수작업 2~3시간) | 타이머 측정 |

> **PoC에서 검증하지 않아도 되는 것:**  
> 예측 정확도, 운영 안정성, 보안 적합성 — 이는 Phase 2 이후 과제입니다.

## 6. 리스크 및 대응

| 리스크 | 발생 가능성 | 대응 방안 |
|--------|-----------|---------|
| 현장 데이터 수령 지연 | 높음 | Week 1부터 요청 시작, 안 오면 가상 데이터로 선행 개발 |
| 작업일보 양식이 너무 다양 | 중간 | 가장 많은 양식 1~2개에 집중, 범용화는 Phase 2에서 |
| Parser LLM 정확도 부족 | 중간 | 프롬프트 반복 튜닝, WBS 구조를 프롬프트에 명시적으로 포함 |
| Claude API 비용 초과 | 낮음 | PoC 규모 (100건 미만)에서는 $10 이내 — 개인 부담 가능 |
| 1개월 내 완성 불가 | 중간 | Week 2 체크포인트(Parser 완성)까지만 해도 개념 증명으로 충분 |

## 7. PoC 이후 — 다음 단계 조건

PoC 완성 후 Phase 2로 넘어가려면 아래가 확보되어야 합니다.

- **데이터 파이프라인:** 실제 이메일·카카오톡 연동 (IT 보안 승인 필요)
- **운영 환경:** 사내 AI 인프라 또는 승인된 클라우드 서버
- **참여 인력:** 현장 담당자 1명의 정기적 H-i-L 참여 (주간 30분)
- **누적 데이터:** Forecaster(D-14 탐지) 활성화를 위한 2개월치 실적 데이터

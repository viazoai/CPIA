# CPIA PoC v2 구현 가능성 시뮬레이션

> **분석 대상:** 통합작업일보_M15X Ph-3 IBL PJT (09/25) + WBS공정표_M15X IBL PH-3
> **분석 목적:** v2 실행계획의 각 파이프라인 단계가 실제 데이터로 작동 가능한지 검증
> **작성일:** 2026.05

---

## 요약 판정

| 파이프라인 단계 | 구현 가능성 | 핵심 이슈 |
|---|---|---|
| Collector / Parser | ✅ 가능 | 시트 구조 파악 완료, 텍스트 추출 straightforward |
| Mapper | ✅ 가능 | 작업내용 텍스트 → WBS 매핑 LLM으로 충분 |
| **Atomizer (Vector DB 설계)** | ⚠️ 조건부 가능 | 인원-물량 직접 연결 불가 → 설계 변경 필요 |
| Reporter | ✅ 가능 | 시트1+4 데이터로 통합 보고서 생성 가능 |
| **Forecaster** | ⚠️ Synthetic history 필수 | 단일 날짜 데이터 → 과거 비교 불가 |
| **Optimizer** | ⚠️ 조건부 가능 | RC 공종 완료 상태, 진행 공종으로 전환 필요 |
| Dashboard | ✅ 가능 | Streamlit으로 충분 |

**결론:** 파이프라인 자체는 구현 가능하나, **Vector DB 설계와 데이터 연결 방식에 근본적 재설계가 필요합니다.**


### 1-3. 인원-물량 연결 구조 문제 (Vector DB 설계의 핵심 장애물)

v2 실행계획에서 가정한 레코드:
```json
{
  "contractor": "남웅건설",
  "trade": "거푸집",
  "headcount": 14,
  "output": 320,        ← 시트4에서
  "productivity": 22.9  ← 계산값
}
```

실제로 연결하려면:
- 인원: 시트1 (업체별 총 인원수, 작업 구분 없음)
- 물량: 시트4 (업체별 작업항목별 수량, 인원 없음)

**연결 시 발생하는 문제:**

```
남웅건설 PH_X-001 금일 인원: 주간 5명
남웅건설 PH_X-001 시트4 작업항목: 철근 배근, 거푸집 설치, 기초 타설 등 수십 건

질문: "오늘 거푸집 작업에 몇 명이 투입됐나?"
대답: 알 수 없음. 5명이 전부 거푸집 했는지, 2명은 철근 나머지 3명이 거푸집 했는지 데이터 없음.
```

이 문제는 이 작업일보 양식의 **구조적 한계**입니다.

## 2. Vector DB 설계: 데이터 실체 기반 재설계

### 2-1. 원래 가정 vs. 실제 가능한 설계

| 항목 | v2 가정 | 실제 가능한 설계 |
|---|---|---|
| 원자화 단위 | 공종별 작업 레코드 | **업체별 일일 작업 레코드** |
| 생산성 메타데이터 | 공종별 output/headcount | **업체 전체 총인원 + 대표 물량항목** |
| 임베딩 텍스트 | 공종별 작업내용 | **업체별 종합 작업내용 (시트1 H열)** |
| 연결 방식 | 공종으로 직접 연결 | **업체코드(BP)로 JOIN** |

### 2-2. 현실적 Vector DB 레코드 설계

```python
# 실제 구현 가능한 레코드 구조
{
    # --- 식별자 ---
    "id": "2025-09-25_PH_X-001",
    
    # --- 메타데이터 (필터·집계용) ---
    "date": "2025-09-25",
    "bp_code": "PH_X-001",
    "bp_name": "남웅건설",
    "scope": "FAB F02,F03,F04,F06 B1F~PH2F",
    "dis": "건축",
    
    # 인원 (시트1 기준 전체 인원)
    "headcount_early": 0,
    "headcount_day": 5,
    "headcount_ext": 0,
    "headcount_total": 5,
    
    # 대표 물량 (시트4에서 금일 실적 있는 최대 항목)
    # → 금일 실적 없을 경우 누계 기준 대표 항목 선택
    "rep_work": "거푸집 설치",
    "rep_unit": "m²",
    "rep_today_qty": 0,
    "rep_cum_progress_pct": 99.8,
    
    # 계산값
    "overtime_ratio": 0.0,  # 연장/(주간+연장)
    
    # --- 임베딩 대상 content ---
    "content": "FAB F03 4F. PH1 패드천공 및 조립 / 전일: FAB F06 PH1 거푸집 설치 / 명일: FAB F03 PH1 EPS블럭·거푸집 설치"
}
```

### 2-3. 임베딩 content 구성 전략

시트1 H열(금일) 단독으로는 텍스트가 너무 짧습니다. **전일+금일+명일 + 구역 정보를 합쳐야** 의미 있는 임베딩이 됩니다.

```python
def build_content(row_sh1, row_sh4_list):
    """
    시트1 행 + 시트4 해당 업체 물량 목록 → 임베딩용 content 생성
    """
    parts = []
    
    # 1. 구역/공종 컨텍스트
    parts.append(f"[{row_sh1['scope']}]")
    
    # 2. 전일/금일/명일 작업 흐름 (3일 맥락)
    if row_sh1['prev_work']:
        parts.append(f"전일: {row_sh1['prev_work']}")
    parts.append(f"금일: {row_sh1['today_work']}")
    if row_sh1['next_work']:
        parts.append(f"명일: {row_sh1['next_work']}")
    
    # 3. 시트4 진행 중인 물량 항목 (잔여 있는 것만)
    active_items = [r for r in row_sh4_list if r['remain'] and r['remain'] > 0]
    if active_items:
        items_str = " / ".join([f"{r['work']}({r['progress_pct']:.0f}%완료)" for r in active_items[:5]])
        parts.append(f"진행물량: {items_str}")
    
    return " | ".join(parts)

# 예시 output:
# "[FAB F02~F06 B1F~PH2F] | 전일: FAB F06 PH1 거푸집 설치 | 금일: FAB F03 4F 패드천공 및 조립 | 명일: FAB F03 PH1 EPS블럭·거푸집 설치 | 진행물량: 철근배근(100%완료) / 기초거푸집(100%완료)"
```

### 2-4. 생산성 추정 방법 (직접 계산 불가 → 대리 지표 사용)

공종별 생산성 직접 계산이 불가능하므로, **업체 레벨의 대리 지표**를 사용합니다.

```
[사용 가능한 대리 지표]

1. 업체 일일 투입 인원 (시트1)
   → "오늘 이 업체가 몇 명 투입했나"

2. 시트4 당일 물량 소화율
   → "금일 실적 / 최근 평균 금일 실적"
   (여러 날 데이터가 쌓이면 계산 가능)

3. 공정률 변화 속도
   → WBS 주차별 WV에서 "이번 주 WV 증가분 / 지난 주 WV 증가분"
   (공정 가속/감속 여부)

4. 작업 집중도 지표
   → 시트4 금일 실적 건수 / 전체 잔여 건수
   (여러 작업 동시 진행 vs 집중 작업)
```

## 3. 파이프라인 단계별 구현 가능성 상세

### 3-1. Collector / Parser ✅ 가능

```python
# 실제 파싱 가능한 정보
sheet1_fields = {
    "bp_code": "row[4]",          # PH_X-001
    "scope": "row[5]",            # FAB F02,F03...
    "prev_work": "row[6]",        # G열
    "today_work": "row[7]",       # H열
    "next_work": "row[8]",        # I열
    "headcount_early": "row[9]",  # 조출
    "headcount_day": "row[10]",   # 주간
    "headcount_ext": "row[11]",   # 연장
}

sheet4_fields = {
    "bp_code": "row[4]",
    "work_content": "row[7]",     # H열 (작업 내용)
    "unit": "row[8]",
    "total_qty": "row[9]",
    "prev_cum": "row[10]",
    "today_qty": "row[11]",
    "cum_qty": "row[12]",
    "remain_qty": "row[14]",
}
```

**주의사항:** 시트1과 시트4 모두 병합셀로 인해 BP코드, 업체명이 첫 행에만 있고 이하 행은 None입니다. Parser에서 forward-fill 처리가 필수입니다.

### 3-2. Mapper ✅ 가능

```
Mapper 입력: Parser 출력 JSON
Mapper 할 일: work_content 텍스트 → WBS L7 코드 매핑

예시:
"철근 배근" → A-03-010 (RC 철근)
"기초 거푸집 설치" → A-03-020 (RC 거푸집)
"기초 타설" → A-03-030 (RC 콘크리트)
"단열재 설치" → A-09-070 (마감)
"패드천공 및 조립" → A-03-010 (RC 부대작업)

판단: LLM이 충분히 처리 가능. 693개 고유 작업내용 중 RC 관련 약 20개.
확신도 낮을 항목: "슈퍼데크 설치", "MOLD-TR" 등 설비 경계 항목.
```

### 3-3. Atomizer ⚠️ 설계 변경 필요

**원래 설계의 문제:**
- 공종별 생산성 계산값을 메타데이터로 저장하려 했으나 계산 불가
- 날짜별 이력이 없어 첫 날 적재 시 "과거 기록" 없음

**수정된 설계:**

```python
def atomize(sheet1_row, sheet4_rows, wbs_row=None):
    """
    1레코드 = 1업체 1일 (공종 단위가 아님)
    """
    # content = 3일 맥락 + 진행 물량 요약
    content = build_content(sheet1_row, sheet4_rows)
    
    # 메타데이터 = 필터·집계에 필요한 구조화 정보
    metadata = {
        "date": extract_date_from_header(),  # 시트 제목에서
        "bp_code": sheet1_row["bp_code"],
        "bp_name": sheet1_row["company"],
        "scope": sheet1_row["scope"],
        "headcount_total": sum([early, day, ext]),
        "overtime_ratio": ext / (day + ext) if (day + ext) > 0 else 0,
        "active_items_count": len([r for r in sheet4_rows if r["remain"] > 0]),
        "today_qty_count": len([r for r in sheet4_rows if r["today_qty"] > 0]),
        "dis": infer_dis_from_scope(),  # 건축/설비/전기 등
    }
    
    # WBS 데이터 연결 (가능한 경우)
    if wbs_row:
        metadata["wbs_spi"] = calc_spi(wbs_row)  # 실적WV / 계획WV
        metadata["plan_complete"] = wbs_row["P_Finish"]
    
    return {"id": f"{date}_{bp_code}", "content": content, "metadata": metadata}
```

**결론:** Atomizer는 "공종별 생산성 레코드"가 아니라 **"업체별 일일 작업 컨텍스트 레코드"** 단위로 재설계해야 합니다.

### 3-4. Forecaster ⚠️ Synthetic history 없이는 작동 불가

**Cold Start 문제 수치화:**

```
현재 데이터: 1일치 (09/25)
의미있는 유사도 검색 최소 기준: 동일 업체 동일 계절 10건 이상
필요 기간: 최소 2~3주 (업무일 기준)

→ Synthetic history 없이 PoC 데모 불가
```

**Synthetic history 생성 기준 (데이터 분석 기반):**

실제 데이터에서 관찰된 패턴:
- 남웅건설 FAB: 주간 5명 수준 (마무리 단계, 9월 기준)
- 남웅건설 CUB: 주간 5명 + 연장 2명 (야간 연장 포함)
- RC 공종 진행 피크: WBS 기준 7~8월 (현재는 완료 단계)

PoC 데모용으로는 **진행 중인 공종**을 대상으로 합니다. 현재 진행 중인 공종 예:
- Deck Plate 설치 (PH_X-032, 진도율 97.3%) → 거의 완료
- 석고벽체 설치 (PH_X-070, 진도율 27~66%) → **진행 중** ✅
- 외장판넬 (PH_X-098, 진도율 87.6%) → 마무리 단계

**PoC 대상 공종 변경 권고:**
RC(철근/거푸집/콘크리트)는 M15X Ph-3에서 완료 상태.
**수장 공종(석고벽체, 수장 마감)** 또는 **외장판넬**이 현재 진행 중이어서 시뮬레이션 적합.

### 3-5. Optimizer ⚠️ 작동은 가능, 단 조건 변경 필요

RC 공종이 완료이므로 **시나리오 공종을 변경**하면 작동 가능합니다.

현재 진행 중 + Optimizer 의미있는 공종:

```
석고벽체 (PH_X-070 광건티엔씨):
  - 3개 스코프: 진도율 27.6% / 48.3% / 66.9%
  - 금일 실적: 10~20 m²/일
  - 잔여: 1,191 + 2,385 + 5,657 = 9,233 m²
  - 현재 pace가 유지되면 완료까지 수개월

외장판넬 (PH_X-098):
  - 진도율 87.6%, 잔여 6,460 m²
  - 금일 실적: 54 m²
  - pace: 6,460 / 54 = 약 120일 → 완료 위협
```

이 공종들로 Forecaster → Optimizer 흐름을 구성하면 됩니다.

## 4. Forecaster/Optimizer가 할 수 있는 판단의 실제 예시

데이터 실체 기반으로 실제 작동 모습을 구체화합니다.

### Case 1: 정상 판단 (석고벽체)

```
[Forecaster 입력]
오늘 작업내용: "석고벽체설치 / FAB 2~4층"
오늘 실적: 10 m² (PH_X-070, 주간 10명)
유사 과거 (Synthetic): 맑음, 정상일 평균 25 m²/10명

[Forecaster 판단]
오늘 생산성: 1.0 m²/인 (평균 2.5 m²/인 대비 -60%)
작업내용 분석: 단순 기재, 특이사항 없음
판단: ⚠️ 이상 — 정상 조건임에도 생산성 현저히 낮음
원인 추론: 작업내용이 너무 짧아 맥락 부족. 구역 이동 또는 자재 부족 가능성.
```

### Case 2: 조건 감안 정상 (야간 연장 다음날)

```
[Forecaster 입력]
오늘 작업내용: "CUB 9층 단열재 설치"
오늘 인원: 주간 5명 + 연장 2명
전일 작업: "CUB 9층 단열재 설치" (동일)
유사 과거 (Synthetic): 연속 연장근무 후 익일 생산성 -15% 패턴

[Forecaster 판단]
오늘 생산성: 계산 필요
overtime_ratio: 2/(5+2) = 28%
판단: ✅ 연장 근무 지속 상태, 컨디션 저하 예상
권고: 연장 비율 3일 연속 시 익일 추가 저하 경고 발령
```

### Case 3: Optimizer 조언 예시

```
[Optimizer 입력]
공종: 외장판넬 (PH_X-098)
오늘 실적: 54 m²
잔여: 6,460 m²
현재 pace 기준 완료일: 오늘 + 120일

[Vector RAG 조회]
유사 상황 (잔여 > 5,000 m², 금일 실적 < 60 m²): 5건 검색
패턴: 3건은 인원 집중 후 회복, 2건은 자재 공급 이슈

[Optimizer 조언]
"현재 외장판넬 pace는 계획 완료일보다 현저히 지연됩니다.
 유사 상황 과거 5건 중 3건은 투입 인원 증가로 pace 2배 개선.
 금일 작업내용에 자재 관련 언급 없음 → 인원 가용 여부 확인 권고.
 이 pace 유지 시 D+120 완료 예상 (계획 대비 +45일)"
```

## 5. 발견된 구조적 한계와 해결 방안

### 한계 1: 인원-물량 직접 연결 불가

| 문제 | 원인 | 해결 방안 |
|---|---|---|
| 공종별 생산성 계산 불가 | 시트1(인원)과 시트4(물량)가 업체 단위로만 연결됨 | 업체 전체 인원 + 대표 물량 항목으로 추정 생산성 사용 |
| 직종별 인원 분리 불가 | 시트2 RC 직종이 개별 업체에 없음 | 소계 그룹(FAB/CUB) 기준으로 집계, 업체 비례 배분 |

**실용적 해결:** "오늘 이 업체가 이 공종에 집중했나"는 **작업내용 텍스트 + 시트4 금일 실적 건수 비율**로 추정 가능.

### 한계 2: 날짜별 이력 없음 (단일 스냅샷)

| 문제 | 원인 | 해결 방안 |
|---|---|---|
| Vector RAG 비교 불가 | 과거 기록이 없음 | Synthetic history 30일치 생성 (Week 1 필수) |
| 시계열 분석 불가 | 날짜별 파일이 아닌 단일 일보 | 실운영 시 매일 작업일보 누적 → 자연 해소 |

**Synthetic history 설계 기준:**
```python
# 실제 데이터에서 관찰한 패턴 반영
patterns = {
    "normal_day":     {"productivity_factor": 1.0, "overtime_ratio": 0.3},
    "rainy_day":      {"productivity_factor": 0.80, "overtime_ratio": 0.2},
    "overtime_heavy": {"productivity_factor": 0.90, "overtime_ratio": 0.55},
    "equipment_wait": {"productivity_factor": 0.65, "overtime_ratio": 0.1},
    "material_short": {"productivity_factor": 0.70, "overtime_ratio": 0.2},
    "multi_tasking":  {"productivity_factor": 0.85, "overtime_ratio": 0.35},
}
# 남웅건설 실측값 기반: 야간연장 비율 47~51% (이전 분석 결과)
# 석고벽체 금일 실적: 10~20 m² (현재 데이터)
```

### 한계 3: RC 공종 완료 (PoC 시나리오 변경 필요)

M15X Ph-3의 남웅건설 RC(철근/거푸집/콘크리트)는 09/25 기준 완료.
**PoC 대상 공종을 변경해야 합니다.**

**권고 공종 변경:**

| 구분 | v2 계획 | 권고 변경 |
|---|---|---|
| 주요 공종 | RC (철근/거푸집/콘크리트) | **수장 (석고벽체) + 외장판넬** |
| 대상 업체 | 남웅건설 | **광건티엔씨(PH_X-070) + 글로벌유명FAB(PH_X-098)** |
| 변경 이유 | RC 완료 상태 | 수장/외장은 진행 중이고 잔여물량 명확 |

또는 **다른 현장 데이터 사용** (Y-1 등 RC 진행 중인 현장).

## 6. 최종 권고: 수정된 Vector DB 설계

### 레코드 단위
- **1레코드 = 1업체 × 1일** (공종별 분리 없음)
- 공종별 물량은 해당 업체의 시트4 데이터 목록으로 포함

### 임베딩 대상 (content 필드)
```
"[구역/스코프] | 전일: [작업내용] | 금일: [작업내용] | 명일: [작업내용] | 진행물량: [공종(진도%)/...]"
```
→ 3일 맥락 + 물량 상태 = 충분한 의미적 밀도

### 메타데이터 필드 (필터·집계용)
```python
{
    "date": str,                    # YYYY-MM-DD
    "bp_code": str,                 # PH_X-001
    "dis": str,                     # 건축/설비/전기
    "headcount_total": int,         # 당일 전체 인원
    "overtime_ratio": float,        # 연장/(주간+연장)
    "active_items": int,            # 잔여있는 물량항목 수
    "today_items": int,             # 금일 실적있는 항목 수
    "wbs_spi": float,               # WBS 기반 SPI (연결 가능한 경우)
    "progress_pct": float,          # 대표 공종 진도율
}
```

### 조회 예시 (Forecaster용)
```python
# 쿼리: "오늘과 유사한 업체 상황의 과거 기록"
results = vector_db.query(
    query_text=today_content,       # 오늘 작업 컨텍스트
    filter={
        "bp_code": "PH_X-070",      # 동일 업체
        "dis": "건축",               # 동일 공종
    },
    n_results=5
)
```

## 8. 종합 판단

**v2 실행계획은 구현 가능합니다.** 단, 아래 3가지를 조정해야 합니다.

1. **Vector DB 원자화 단위**: 공종별 → 업체별 일일 레코드
2. **PoC 대상 공종**: RC(완료) → 수장/외장 (진행 중)
3. **Synthetic history**: Week 1 핵심 선행 과제로 실제 패턴 기반 생성 필수

이 조정 후 파이프라인 전체 흐름은 **현재 데이터로 실증 가능**합니다.
핵심 AI 가치(Mapper 시멘틱 매핑 + Forecaster 컨텍스트 기반 판단 + Optimizer 조언 생성)는
위 한계에도 불구하고 유효하게 작동할 수 있습니다.
